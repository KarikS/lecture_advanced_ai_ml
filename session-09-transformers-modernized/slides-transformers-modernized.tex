\begin{itemize}

\begin{frame}{Compute vs.\ Memory}
\begin{itemize}
  \item A GPU can do arithmetic much faster than it can move data between its memory and its compute units.
  \item The number of arithmetic operations per byte moved is an operation's \textbf{arithmetic intensity}. With low arithmetic intensity, an operation is limited by \textbf{memory traffic}, not by the number of floating-point operations (FLOPs).
  \item Matrix multiplications do many operations per byte loaded; normalizations and element-wise operations do few.
  \item So an operation can account for a tiny share of the FLOPs and still a noticeable share of the runtime --- the next slides use exactly this argument.
  \item Hardware details follow in session 12.
\end{itemize}
\end{frame}

\begin{frame}{More generally: dropping bias terms}
% hand-typeset (_generator/handwritten/)
\textbf{Most modern transformers don't have bias terms.}

\bigskip
Original Transformer:
\[ \text{FFN}(x) = \max(0, xW_1 + b_1)\,W_2 + b_2 \]
Most implementations (if they're not gated):
\[ FFN(x) = \sigma(xW_1)\,W_2 \]
\medskip
{\centering \textbf{Reasons:} memory (similar to RMSnorm) and optimization stability\par}
\end{frame}

% CS336 slide 19
\begin{frame}{LayerNorm: recap}
\begin{itemize}
  \item Basically everyone does pre-norm.
  \item Intuition -- keep the good parts of residual connections
  \item Observations -- nicer gradient propagation, fewer spike
  \item Some people add a second norm outside the residual stream (NOT post-norm)
  \item Most people do RMSnorm
  \item In practice, works as well as LayerNorm
  \item But, has fewer parameters to move around, which saves on wallclock time
  \item People more generally drop bias terms since the compute/param tradeoffs are not great.
\end{itemize}
\end{frame}

\begin{frame}{Gated activations (*GLU)}
% hand-typeset (_generator/handwritten/)
GLUs modify the `first part' of a FF layer
\[ FF(x) = \textcolor{red}{\max(0, xW_1)}\,W_2 \]
Instead of a linear + ReLU, augment the above with an (entrywise) linear term
\[ \textcolor{red}{\max(0, xW_1)} \rightarrow \max(0, xW_1) \otimes (xV) \]
This gives the gated variant (ReGLU) -- note that we have an extra parameter ($V$)
\[ \text{FF}_{\text{ReGLU}}(x) = (\max(0, xW_1) \otimes xV)\,W_2 \]
\end{frame}

% CS336 slide 31
\begin{frame}{RoPE: rotary position embeddings}
% hand-typeset (_generator/handwritten/)
\small
\textbf{High level thought process:} a \emph{relative} position embedding should be some $f(x, i)$ s.t.
\[ \langle f(x, i), f(y, j) \rangle = g(x, y, i - j) \]
That is, the attention function \emph{only} gets to depend on the relative position ($i-j$). How do existing embeddings not fulfill this goal?
\begin{itemize}
  \item \textbf{Sine:} Has various cross-terms that are not relative
  \[ \langle \mathit{Embed}(x, i), \mathit{Embed}(y, i) \rangle = \langle v_x, v_y \rangle + \langle PE_i, v_y \rangle \ldots \]
  \item \textbf{Absolute:} obviously not relative
  \item \textbf{Relative embeddings:}
  \[ e_{ij} = \frac{x_i W^Q \left(x_j W^K + a_{ij}^K\right)^T}{\sqrt{d_z}} \quad \text{is not an inner product} \]
\end{itemize}
\end{frame}

% CS336 slide 32
\begin{frame}{RoPE: rotary position embeddings}
% hand-typeset (_generator/handwritten/)
\textbf{How can we solve this problem?}
\begin{itemize}
  \item We want our embeddings to be \textbf{invariant to absolute position}
  \item We know that inner products are invariant to arbitrary rotation.
\end{itemize}

{\ttfamily\fontsize{6.4}{7.6}\selectfont query\_states = self.q\_proj(hidden\_states)\\
key\_states = self.k\_proj(hidden\_states)\\
value\_states = self.v\_proj(hidden\_states)\\

% CS336 slide 37
\begin{frame}{Surprising (?) consensus hyperparameter 1}
% hand-typeset (_generator/handwritten/)
Feedforward -- model dimension ratio.
\[ \text{FFN}(x) = \max(0, xW_1 + b_1)\,W_2 + b_2 \]
There are two dimensions that are relevant -- the feedforward dim ($d_{ff}$) and model dim ($d_{model}$). What should their relationship be?
\[ \boldsymbol{d_{ff} = 4\, d_{model}} \]
This is \emph{almost always} true. There's just a few exceptions.
\end{frame}

\begin{itemize}

  \item GQA / MQA : Saving inference costs by reducing the number of heads
  \item Sparse or sliding window attention (GPT4/Mistral): restricting the attention pattern

% [O] original bridge frame (draft for the user to rewrite); listed in order.txt
\begin{frame}{The KV Cache}
\begin{itemize}
  \item Autoregressive generation (session 8, decoding) produces one token at a time; each new token attends to all previous tokens.
  \item The keys and values of the previous tokens do not change, so they are stored instead of recomputed: the \textbf{KV cache}.
  \item Its size grows with sequence length $\times$ number of layers $\times$ number of heads $\times$ head dimension (per sequence in the batch).
  \item At inference time, reading this cache from memory --- not the arithmetic --- is often the bottleneck. The following attention variants reduce it.
\end{itemize}
\end{frame}

% FRAMES-BEGIN l3 59 68
% CS336 slide 59

\begin{frame}{GQA/MQA -- Reducing attention head cost}

\[ (\overset{\text{\scriptsize X}}{bn^2 d} + \overset{\text{\scriptsize projection}}{nd^2}) \]

\footnotesize
\makebox[\textwidth][c]{\begin{minipage}{400pt}
\textbf{Basic idea:} express the Q, K, V as functions of a lower-dim, `latent' activation
\begin{center}
\includegraphics[page=45,trim=297 211 297 95,clip,width=\linewidth,height=48pt,keepaspectratio]{figure/cs336-l4.pdf}\hspace{14pt}\includegraphics[page=45,trim=439 206 66 100,clip,width=\linewidth,height=48pt,keepaspectratio]{figure/cs336-l4.pdf}
\end{center}
\textbf{Benefits:} when KV-caching, we only need to store $c_t^{KV}$, which can be much smaller.
$W^{UK}$ can be merged into the Q projection\\
\mbox{}\hfill(they also compress queries, for memory savings during training)\quad\raisebox{-0.4\height}{\includegraphics[page=45,trim=561 110 72 239,clip,width=\linewidth,height=20pt,keepaspectratio]{figure/cs336-l4.pdf}}

\textbf{Complexity:} rope conflicts with MLA-style caching.\\[2pt]
\hspace*{1em}Without RoPE -- $\langle Q, K \rangle = \langle hW^Q, W^{UK} c_t^{KV} \rangle = \langle h\,\textcolor{red}{W^Q W^{UK}}, c_t^{KV} \rangle$\\[2pt]
\hspace*{1em}With RoPE -- $\langle QR_q, R_k K \rangle = \langle hW^Q R_q, R_k W^{UK} c_t^{KV} \rangle = \langle h\,\textcolor{red}{W^Q R_q R_k W^{UK}}, c_t^{KV} \rangle$\par\smallskip
{\centering\color{gray} The solution -- Have a few non-latent key dimensions that can be rotated\par}
\end{minipage}}
\end{frame}

\section{Where This Is Going}

\begin{frame}{Where This Is Going}
\begin{itemize}
  \item The changes in this session act on the Transformer \emph{block}, not on the type of data.
  \item Vision Transformers use them too, e.g.:
  \begin{itemize}
    \item ViT-22B: parallel layers, QK normalization, no biases on the QKV projections and LayerNorms \citebutton{Dehghani et al., 2023}{https://arxiv.org/abs/2302.05442};
    \item V-MoE: a sparse mixture-of-experts Vision Transformer \citebutton{Riquelme et al., 2021}{https://arxiv.org/abs/2106.05974}.
  \end{itemize}
  \item Session 10 takes the Transformer to images, multimodal data and video.
\end{itemize}
